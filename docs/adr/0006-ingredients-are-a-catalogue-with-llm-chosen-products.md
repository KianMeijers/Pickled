# Ingredients are a catalogue, and an LLM picks each store's Product once

To price a Meal Plan and match Deals, every ingredient line has to reach a store product. Searching a store for "kipfilet" finds dozens of candidates, from sandwich slices to organic fillet, so the hard part is choosing one, not finding them. We keep a catalogue of **Ingredients** (a canonical name plus aliases, an aisle, a pantry flag and grams per piece). Recipes (through structured lines from the agent's `save_recipe` tool), Deals (through a `tag_deals` LLM job after each fetch) and Seasonal Produce (at import) all link to it. For each Ingredient and store, a code-built shortlist goes to the match model, which picks one **Product** once. The choice is stored and reused across Meal Plans, and the Household can correct it in chat. We considered matching in code only (deterministic, but it picks the wrong product, such as sandwich slices for a stir-fry) and letting the agent match every time (good picks, but slow and costly, and it repeats the same choices every week while spending the request budget in ADR 0005). The catalogue makes matching an LLM step at ingestion and lookup time, and makes `ingredients/` a module that `deals/`, `seasonal/` and `planning/` all depend on.
