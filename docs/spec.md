# Pickled v1 spec

This spec is the build reference for Pickled v1. It brings together the decisions on the [Pickled v1 architecture](https://github.com/KianMeijers/Pickled/issues/1) map. Each decision's reasoning lives in its ticket or ADR (`docs/adr/`), and this page only states the result. Domain words (Household, Meal Plan, Meal, Deal, Ingredient, Product, …) mean what `CONTEXT.md` says they mean.

## 1. What v1 is

- A chat-based weekly meal planner for **one Household** with no login. It is a mobile-first web app, run locally with Docker Compose.
- Each week the agent drafts a **Meal Plan**: dinners only, running from Saturday (the Shopping Day) to Friday. It is built from the AH and Jumbo **Deals** valid on that Saturday, this month's **Seasonal Produce**, the **Taste Profile** and any **Food Goals**. The Household then reviews and changes the plan in that plan's **Conversation**, and accepts it.
- The plan produces a **Shopping List** (one winning store, grouped by aisle) and two cost figures: a meal cost and a shopping cost. **Recipes** are generated by the agent and saved for reuse.
- Everything the Household sees is in Dutch. Code and prompts are in English.

**Out of scope:** multiple Households and login; Recipe images; exporting to store apps or baskets; importing your own Recipes; learning taste from ratings or signals; and running online (hosting, backups, access control, CI, push notifications). Moving online is its own later effort.

## 2. Stack and runtime

| Concern | Choice | Source |
|---|---|---|
| Language and tooling | Python 3.14, uv, ruff, pytest | — |
| Web | FastAPI + Jinja + HTMX, our own SSE endpoint for streaming | [#6](https://github.com/KianMeijers/Pickled/issues/6) |
| Database | Postgres (pgvector image, `pg_trgm`), SQLAlchemy 2.0, Alembic | [#6](https://github.com/KianMeijers/Pickled/issues/6) |
| Agent | LangChain `create_agent` inside the FastAPI app, with the LangGraph `AsyncPostgresSaver` | ADR 0001, ADR 0004 |
| LLM | Runware's Anthropic-compatible `/v1/messages`, through `ChatAnthropic` | ADR 0004 |
| Background jobs | Procrastinate (a queue in Postgres) in a separate `pickled worker` process | ADR 0002 |
| Local runtime | Compose runs Postgres. The app and worker run on the host (`uv run`, hot reload). A Compose profile runs both from the Dockerfile | [#6](https://github.com/KianMeijers/Pickled/issues/6) |
| Tracing | Our own `llm_call` table; LangSmith opt-in only | ADR 0009 |

Dependencies: replace `anthropic` with `langchain`, `langchain-anthropic` and `langgraph-checkpoint-postgres`, and add `fastapi`, `jinja2`, `sqlalchemy`, `alembic`, `psycopg`, `procrastinate` and `httpx`.

## 3. Modules

```
src/pickled/
  stores/       shared HTTP client setup (browser/app User-Agent), the Appie API's token and headers,
                per-store weekly request counter
  ingredients/  Ingredient catalogue, Product per store, price observations, lookup chain,
                RegularPriceSource port (AhSearchPriceSource, CheckjebonJumboPriceSource)
  deals/        DealSource port (AhDealSource, JumboDealSource), discount parsing, upsert/withdraw,
                deals_valid_on(date, store=None, channel=IN_STORE)
  seasonal/     seasonal_produce table + `pickled seasonal import`
  planning/     Meal Plan, Meal, Recipe, Shopping List, plan summary (costs, checks, warnings)
  taste/        Household, Taste notes, Food Goals
  llm/          make_chat_model(role), price_of(model, usage), llm_context, llm_call recording, balance check
  agent/        create_agent setup, prompts/ (Jinja), tools/ (thin wrappers over domain interfaces)
  jobs/         Procrastinate app, job definitions, schedules
  web/          FastAPI routes, templates, SSE
  evals/        eval runner, checks, judge (scenarios and results live in /evals at the repo root)
```

The dependency rules:
- `deals`, `seasonal` and `planning` depend on `ingredients`, which depends on `stores`.
- Domain modules never import `agent`, `web` or `jobs`.
- Each module owns its tables. Database foreign keys between modules are allowed, but code reads another module's tables only through that module's interface.

## 4. Data model

The conventions:
- `bigint` identity keys.
- Money in integer cents (LLM spend in USD `numeric`).
- `timestamptz` for timestamps and `date` for days, with Europe/Amsterdam as the business timezone.
- Quantities as `numeric`.
- History is kept forever. The exceptions are `deal_fetch`, where the last ~8 per source are kept, and `checkjebon_product`, a copy of outside data replaced when it changes (the prices we used stay in `price_observation`).

Details: [What is the core data model?](https://github.com/KianMeijers/Pickled/issues/10).

| Table | Module | Holds |
|---|---|---|
| `household` | taste | single row: `people`, optional name. No `household_id` foreign keys anywhere |
| `taste_note` | taste | text (≤ 200 chars), `author` (`agent`/`user`), `archived_at`. ~30 active at most |
| `food_goal` | taste | `kind` (`kcal_per_day`, `protein_g_per_day`, `vegetarian_days_per_week`, `budget_cents_per_week`, `other` + text), `min`/`max`, `active` |
| `meal_plan` | planning | `week_start` (unique, a Saturday), `status` (`draft`→`accepted`, one way), `accepted_at`, `store`, `people` snapshot, `est_cost_cents` (shopping cost), `drafted_at` (unset on a partial draft) |
| `meal` | planning | `(meal_plan_id, date)`; `recipe_id` + `servings`, **or** `leftovers_of` → an earlier Meal; deliberately empty days are recorded |
| `recipe` | planning | immutable: title, base servings, steps (markdown), tags, estimated nutrition per serving, `derived_from_id` |
| `recipe_ingredient` | planning | `ingredient_id`, quantity, unit (`g`/`ml`/`piece`/`tbsp`/`tsp`/`pinch`/`to_taste`), note |
| `shopping_list_item` | planning | name, `ingredient_id`, quantity, unit, `source` (`recipe`/`manual`), pantry flag, `deal_id`, store, aisle, packs, `est_price_cents`, rough flag, `checked`. Regenerated in place when Meals change; manual items and ticks survive, matched by name |
| `ingredient` | ingredients | name, aliases, aisle, pantry flag, `grams_per_piece`, `keeps_days` |
| `product` | ingredients | at most one chosen per (Ingredient, store): store SKU, name, pack size, link |
| `price_observation` | ingredients | product, price, source (Deal regular price, AH search, Checkjebon), observed at |
| `product_miss` | ingredients | each time the match model found no Product for an (Ingredient, store); not asked again for 4 weeks |
| `checkjebon_product` | ingredients | our copy of Checkjebon's Jumbo half: SKU, name, price, size, link |
| `checkjebon_check` | ingredients | each `refresh_checkjebon` run: content hash, changed, stale, counts |
| `store_request` | stores | per-store, per-week request counter (budget ~60/store/week, ADR 0005 as amended) |
| `deal` | deals | identity `(store, source_id, valid_from)`; raw text, parsed discount kind + params, effective fraction, channel, store category, optional price/was-price/unit size, `withdrawn_at` |
| `deal_ingredient` | deals | Deal → Ingredient links from `tag_deals` (or a non-food mark) |
| `deal_product`, `deal_fetch` | deals | listed products where the source gives them; raw jsonb + counts per run |
| `seasonal_produce` | seasonal | `ingredient_id`, month, `fresh`/`stored` |
| `llm_call` | llm | time, role, model, job / Meal Plan context, 4 token counts, `cost_usd` (null if the model's price is unknown) |
| `llm_balance` | llm | Runware balance + checked at |

**Conversation storage:** the LangGraph checkpointer lives in its own `langgraph` schema. `pickled db upgrade` runs `alembic upgrade` and then `AsyncPostgresSaver.setup()`, and Alembic ignores that schema. The thread id is `meal-plan-{id}`, and we keep no copy of messages.

`deal_ingredient`, `product`, `price_observation`, `store_request` and `llm_balance` are named here for the first time. Their shape follows the decisions in [#16](https://github.com/KianMeijers/Pickled/issues/16) and [#19](https://github.com/KianMeijers/Pickled/issues/19); exact columns are settled when building.

## 5. Outside data

- **Deals** (ADR 0005, [#9](https://github.com/KianMeijers/Pickled/issues/9)):
  - Sources:
    - **AH:** the Appie mobile API, with a fresh anonymous token per run, NATIONAL promotions only.
    - **Jumbo:** the `__NUXT_DATA__` payload on `/aanbiedingen/nu`.
  - Each item is checked with a strict Pydantic model.
  - A run fails, and writes nothing, if more than ~20% of items are skipped or the count falls below 40% of last week's. A failed run keeps the stored copy.
  - Discounts are parsed with regexes into `PERCENT_OFF`, `FIXED_PRICE`, `N_FOR_PRICE`, `BUY_N_GET_M_FREE`, `NTH_HALF_PRICE` and `OTHER`. No LLM is used for parsing.
  - The private-use rules apply: at most ~60 requests per store per week (enforced by `store_request`), no redistribution, and never hosted for others.
- **Ingredient matching** (ADR 0006, [#16](https://github.com/KianMeijers/Pickled/issues/16)):
  - Every name goes through one lookup: normalise, then exact name or alias, then a trigram match above a threshold, otherwise create a new Ingredient.
  - `tag_deals` links Deals to Ingredients in batches of ~50.
  - The first time an Ingredient needs a price at a store, the match model picks one Product from a shortlist: AH search (1 request), or a Jumbo trigram search over Checkjebon. It prefers plain or raw, then the house brand, then the best price per kg.
  - `set_product` corrects a pick.
- **Regular prices** ([#15](https://github.com/KianMeijers/Pickled/issues/15)):
  - **Jumbo:** the Jumbo half of Checkjebon, downloaded weekly. The status line warns if it hasn't changed in more than 3 days. Checkjebon's AH data is never used.
  - **AH:** Appie product search, cached and refreshed after 4 weeks.
  - **Deal products:** their regular price is recorded as an observation.
  - **Rough prices:** a price is marked rough if it's older than 8 weeks or comes from the other store. Totals then show "≈ €X, n items estimated".
- **Seasonal Produce** (ADR 0003, [#12](https://github.com/KianMeijers/Pickled/issues/12)):
  - Comes from the Voedingscentrum calendar. `pickled seasonal import` reads it into Postgres and fails without half-loading; it is never committed or published.
  - Each item is tagged fresh or stored, using a small committed file of storage crops.
  - Covers fruit and vegetables only, including mushrooms, without year-round staples.
  - The app runs without it, and the status line then says so.

## 6. Background jobs

All jobs run on Procrastinate in Europe/Amsterdam time. Every schedule is worked out from `SHOPPING_DAY = Saturday` ([#14](https://github.com/KianMeijers/Pickled/issues/14)), and only one job per (source, week) or (week) can be queued at a time.

| Job | When | Notes |
|---|---|---|
| `fetch_deals(source)` | AH Mon 06:00, Jumbo Wed 06:00, both Thu 17:00 | ~3 retries with backoff; queues `tag_deals` after it |
| `tag_deals(source)` | after each fetch | match model, batches of ~50 |
| `refresh_checkjebon` | weekly | keeps the last good copy if the data looks stale |
| `draft_meal_plan(week)` | Thu 18:00 | retries until Fri 12:00 for missing Deals, then drafts with what's there; also run on redraft and "draft now" |
| `reflect_on_week(meal_plan)` | after the plan's Friday | merges anything lasting from the Conversation into Taste notes |
| `check_llm_balance` | daily | reads Runware `accountManagement`/`getDetails` |

How failures show:
- There are no notifications in v1; a `notify(event)` seam does nothing for now.
- The **status line** is read from the job table and the warnings: last fetch per store, failures, a missing store, stale Checkjebon, missing Seasonal Produce, the spend cap and the balance.
- A **402** from Runware fails a job without retrying.
- At the monthly cap, LLM jobs are skipped.
- `pickled jobs run <job> [--source …]` reruns any job.

## 7. The agent

The shape (ADR 0004, ADR 0007, [#11](https://github.com/KianMeijers/Pickled/issues/11)):
- One `create_agent` agent serves both chat and drafting. A draft is just the first turn of the plan's Conversation.
- Middleware handles the system prompt, `AnthropicPromptCachingMiddleware` and `ModelCallLimitMiddleware`, with limits of **40 calls per draft** and **15 per chat turn**.
- **The agent chooses** the store, the Meals and the Recipes. **Code calculates** everything else, and every write tool returns the **plan summary**: the Shopping List, meal and shopping costs at both stores, Food Goal checks, perishable warnings, split warnings (the other store saves at least €3) and rough-price counts. The agent never states a number it worked out itself.

**Prompt context** (Jinja templates in `agent/prompts/`, cached):
- Household size, active Taste notes and active Food Goals.
- The week's dates and this month's Seasonal Ingredients.
- A table of about 100 lines: the Ingredients on a Deal at each store, with the best effective discount.

**Tools** (`agent/tools/`):
- Read: `get_plan`, `search_deals(ingredient | aisle, store?)`, `search_recipes(query)`, `get_recipe(id)`
- Plan: `set_store`, `set_meal(date, recipe_id, servings)`, `set_leftovers(date, of_date)`, `clear_meal(date)`, `finish_draft(summary)`
- Recipes and Products: `save_recipe(title, servings, steps, tags, nutrition, lines[])`, `set_product(ingredient, store, hint)`
- Shopping List: `add_shopping_item(name, quantity?, unit?)`
- Taste and goals: `add_taste_note`, `update_taste_note`, `archive_taste_note`, `set_food_goal(kind, min, max)`, `clear_food_goal(kind)`

**Rules code enforces:**
- `finish_draft` and accept both require every day to have a Meal or be deliberately empty.
- Write tools refuse any `date < today`.
- A Recipe may not repeat within 3 weeks.
- The agent never rewrites a user-written Taste note; it suggests the change in chat instead.
- Nutrition is checked against a **40% dinner share** of the daily goal per person.
- Vegetarian days and the budget (shopping cost) are checked exactly. A day is vegetarian when its Recipe is tagged `vegetarisch`.
- The split warning adds up what the other store's Deals save on the Shopping List's lines; it fires at €3 or more.
- A partial draft (call limit hit) stays a draft, and the status line says so.

**Model roles:** `make_chat_model(role)` is the only place a model is built. It uses Runware's base URL, a Bearer `Authorization` header, a 120 s timeout and `max_retries=2`. It also attaches the `llm_call` callback.

| Setting | Roles | Default |
|---|---|---|
| `PICKLED_CHAT_MODEL` | `chat` | `claude-sonnet-5-5` |
| `PICKLED_DRAFT_MODEL` | `draft`, `reflect` | `claude-sonnet-5-5` |
| `PICKLED_MATCH_MODEL` | `tag_deals`, `pick_product` | `claude-sonnet-5-5` |
| `PICKLED_JUDGE_MODEL` | `eval_judge` | `claude-sonnet-5-5` |

Opus 5.5 can be turned on per setting. Haiku isn't available on Runware. Prompts never include personal identifiers, and we accept that there's no Zero Data Retention.

## 8. Web app and flows

See [#17](https://github.com/KianMeijers/Pickled/issues/17).

- **Pages:**
  - `/` shows the plan whose week contains today, with a banner when next week's draft exists.
  - `/plans/{week_start}` shows seven day cards, the Conversation, and the Shopping List on a tab.
  - A settings page holds the Household size, Food Goals, Taste notes (showing who wrote each one) and "LLM-kosten".
- **Chat:** chat goes over SSE. The stream carries reply tokens, a status line for each tool step, and a "plan updated" event that swaps the plan panel (HTMX out-of-band).
- **Day buttons:** "Vervang", "Restjes" and "Overslaan" post templated chat messages. Clearing a day calls the plan code directly and adds a system note to the Conversation.
- **Accept:** a one-way flag. It freezes nothing: during the week, chat can still change the days ahead, and the agent prefers items already ticked.
- **Redraft:** allowed only while the plan is a draft. It's a full replace behind a confirm dialog, takes an optional hint and runs as the `draft_meal_plan` job.
- **First run:** onboarding (number of people, Food Goals, a few Taste notes), then fetch both stores and draft the next Shopping Day's plan. "Draft now" is offered whenever the next week has no plan.
- **Concurrency:** a Postgres advisory lock on the plan id is shared by draft jobs and chat turns. While a job runs, the chat input is disabled.
- **Shopping List:** grouped by store, then by aisle (`groente_fruit`, `vlees_vis_vega`, `zuivel_eieren`, `brood`, `voorraad`, `diepvries`, `dranken`, `overig`). Deal lines are marked, and pantry items go in a "check you have" section.

## 9. LLM spend and logs

See ADR 0009 and [#19](https://github.com/KianMeijers/Pickled/issues/19).

- **`llm_call`:** every model call writes a row through the callback in `make_chat_model`. The cost comes from an in-code price table through `price_of(model, usage) -> Decimal`. `with llm_context(job=..., meal_plan=...)` at each entry point says what started the call. A failed write is logged and never breaks the agent.
- **Monthly cap:** `PICKLED_LLM_MONTHLY_CAP_USD` (default $25).
  - At 80%, the status line warns.
  - At 100%, the draft, tag and reflect jobs are skipped. Chat keeps working, with a banner.
  - Evals don't count toward the cap.
- **Balance:** the status line warns below `PICKLED_LLM_MIN_BALANCE_USD` (default $5).
- **LLM-kosten** in settings shows:
  - spend this month and last month by role;
  - spend per Meal Plan week;
  - the balance;
  - the cap;
  - a manual comparison of the drop in balance against the `llm_call` total.
- **Logs:** stdlib `logging` to stdout. One line per tool call and per job start or end, with no prompt text.
- **LangSmith:** turned on only with `LANGSMITH_TRACING=true` plus a key.

## 10. Testing and evals

See ADR 0008 and [#18](https://github.com/KianMeijers/Pickled/issues/18).

- **Tests:**
  - `pytest` runs against the Compose Postgres with a `pickled_test` database, migrated once per session and rolled back per test.
  - The LLM is faked through `make_chat_model` (`GenericFakeChatModel` or a subclass that emits tool calls).
  - Adapters are tested against recorded fixtures, and the seasonal import against a small made-up fixture.
- **Live smoke test:** `pytest -m live`, skipped by default.
- **Evals:**
  - `pickled eval run [--scenario] [--repeats N] [--max-tokens]` runs over the YAML scenarios in `evals/scenarios/`. Results go to `evals/results/` (gitignored).
  - **What's evaluated:** drafts; scripted chat edits (`chat: [{say, touches}]`); and `tag_deals` against `evals/tag_deals/<week>.csv`, scored on precision and recall.
  - **Grading:**
    - The plan summary code supplies the hard failures and the scores.
    - A Dutch-language check covers the user-facing text.
    - An LLM judge answers yes/no per Taste note, on variety, and on whether each chat edit was carried out.
  - **Starter scenarios:** a baseline, a vegetarian-days goal, a tight budget, strong dislikes, and a thin-Deals week.
  - **Building scenarios:** `pickled eval snapshot-deals <date>` freezes a real week's Deals, and `pickled eval capture <week>` turns a bad real week into a scenario.
  - **Comparing:** `pickled eval compare` checks a run against `evals/baseline.json`, which changes only through `pickled eval accept`.
- **The rule** (goes into `CLAUDE.md` when the agent is built): before merging any change to `agent/prompts/`, `agent/tools/`, the model settings, the plan summary or check code, or `tag_deals`, run `pickled eval run --repeats 3 && pickled eval compare`.

## 11. Commands and settings

**Commands:**
- `pickled db upgrade`
- `pickled worker`
- `pickled seasonal import`
- `pickled jobs run <job> [--source …]`
- `pickled eval run | compare | accept | snapshot-deals | capture`
- the FastAPI app itself (uvicorn with reload locally)

**Settings** (`.env`, pydantic-settings):
- `DATABASE_URL`
- `RUNWARE_API_KEY` (replaces `ANTHROPIC_API_KEY`) and `RUNWARE_BASE_URL`
- the four model settings from §7, the LLM timeout and the retry count
- `PICKLED_LLM_MONTHLY_CAP_USD` and `PICKLED_LLM_MIN_BALANCE_USD`
- optionally `LANGSMITH_TRACING` and `LANGSMITH_API_KEY`

Constants, not settings: `SHOPPING_DAY`, the €3 split threshold, the 40% dinner share, the call limits, the request budget and the eval margins.

## 12. Suggested build order

Each step ends with something that runs and is tested.

1. **Skeleton:** settings, Compose Postgres, SQLAlchemy and Alembic, `pickled db upgrade`, the test-DB fixture, and the CLI entry point.
2. **`stores` + `ingredients`:** the catalogue, the lookup chain and the request counter.
3. **`deals`:** both adapters with fixtures, parsing, upsert and withdraw. Then the Procrastinate worker with `fetch_deals` and `pickled jobs run`.
4. **`seasonal`:** the import.
5. **`llm`:** `make_chat_model`, `price_of`, `llm_context`, `llm_call`, and the live smoke test. Then `tag_deals`.
6. **Regular prices:** Checkjebon, AH search and Product picks.
7. **`planning` + `taste`:** Meal Plan, Meals, Recipes, the Shopping List and the plan summary with all its checks, covered by unit tests and no LLM.
8. **`agent`:** prompts, tools, and the `draft_meal_plan` job, tested with fake models.
9. **Evals:** the runner, the starter scenarios and a first baseline, so that every later prompt change is measured.
10. **`web`:** plan pages, SSE chat and the day buttons, then accept, redraft, onboarding and "draft now".
11. **Finishing:** `reflect_on_week`, the spend cap and balance check, the status line, and the settings pages.

## 13. Left open beyond v1

- **Semantic Recipe search (pgvector):** v1 uses trigram and tag search. Add pgvector only if reuse turns out to be poor.
- **Better nutrition (NEVO):** replace LLM nutrition estimates with NEVO data.
- **Fuller Deal data:** expand Deal groups and fetch Jumbo detail pages.
- **Moving online:** a separate effort.
